\begin{abstract}
Rural water security depends heavily on small rainwater-harvesting ponds, yet
choosing where to build one is usually done by eye and gives no quantitative
basis for sizing. This project delivers a working web application that turns that
judgement into an automated, explainable computation. A user selects any land
area on an interactive map; the backend fetches a real Digital Elevation Model
for exactly that area from OpenTopography, reconstructs the terrain, and routes
surface water across it using depression filling, D8 flow direction and flow
accumulation. It then ranks candidate pond sites using topographic wetness and
position indices while explicitly excluding steep ground and the existing
drainage network, delineates the catchment that drains to each site, and measures
areas in a projected coordinate system. Historical rainfall from the Open-Meteo
archive is combined with the catchment and the basin's own geometry to estimate
the water volume that can realistically be collected and the pond depth required
to hold a year's runoff. Every result --- suggested pond, catchment, contours and
existing drainage --- is overlaid on the map, and can be exported as an image,
GeoJSON or JSON. The system is deployed as a single lightweight process on the
provided memory-constrained servers, completes an analysis in about twelve
seconds (instant when cached), and is covered by 71 automated tests. Nothing is
hard-coded to any one location.
\end{abstract}

\keywords{Village Pond Planning, Geospatial Analysis, Rainwater

\section{Introduction}
\label{sec:intro}
Access to water in rural areas is strongly tied to local rainwater harvesting.
Small village ponds (tanks) capture monsoon runoff, recharge groundwater and
provide water through dry months. But their effectiveness depends on \emph{where}
they are built: a pond must sit where the land naturally funnels runoff toward it
and where the ground forms a basin that holds water, rather than on a slope or
inside a stream. Making that judgement well requires reading terrain, estimating
how much land drains to a point, and knowing how much rain falls there.

The goal of this assignment is an AI/geospatial-assisted web application that
performs this reasoning automatically. A user selects a region on a map and the
system recommends suitable pond locations, the catchment feeding each, and the
water volume each could collect --- all visualised on the map. The rest of this
report covers the requirements (Section~\ref{sec:requirements}), the architecture
(Section~\ref{sec:architecture}), the algorithms (Section~\ref{sec:methodology}),
the implementation (Section~\ref{sec:implementation}), the mapping to core system
design themes (Section~\ref{sec:csd-themes}), results and performance
(Section~\ref{sec:results}), and a discussion of limitations
(Section~\ref{sec:discussion}).

\subsection{Motivation}
Manual site selection is slow and inconsistent. A surveyor must walk the land and
infer drainage by eye; there is no centralised, easy way to combine terrain shape
with historical rainfall; and the result is qualitative, offering no basis for
deciding pond depth or storage capacity. An automated tool reduces a large search
space to a small, justified shortlist of sites --- each with quantitative
catchment and volume figures --- that a village administrator can then inspect on
the ground. It also makes the reasoning transparent and repeatable for any
location, not just areas an expert already knows.

\subsection{Scope of the Project}
The system estimates, for a user-selected area: suitable pond locations, the
catchment area draining to each, the pond's own footprint, the expected
collectable water volume, and the depth required to hold a year's runoff, all
overlaid on an interactive map and exportable. It does \emph{not} perform the
civil/structural engineering design of the pond (embankment, spillway, soil
mechanics), it does not detect ponds that already physically exist from satellite
imagery, and it does not model sub-surface hydrogeology. Results are decision
support at survey-shortlist accuracy, bounded by the resolution of freely
available elevation and rainfall data.

\subsection{Non-Functional Requirements}
\textbf{Performance:} a full analysis (including the live DEM fetch) should
complete in well under a minute; repeat analyses of the same area should be
near-instant. \textbf{Resource use:} the service must run within the provided
containers' hard limit of 512\,MB RAM and small storage. \textbf{Availability:}
the server runs detached and stays up independently of any login session.
\textbf{Resilience:} external-API failures must degrade gracefully (documented
fallbacks, clear error messages) rather than crashing an analysis.
\textbf{Usability:} the tool must work in a modern desktop browser with no
installation and no configuration. \textbf{Portability:} the same build must run
unchanged on any of the four provided systems.

\section{System Architecture and High-Level Design}
\label{sec:architecture}
The system is a client plus a single backend service that also serves the client.
The React front-end runs in the browser; it calls one REST endpoint on the FastAPI
backend, which orchestrates two external data APIs (elevation and rainfall) and
the in-process analysis pipeline, then returns a combined JSON payload that the
front-end renders as map overlays. There is no separate database tier
(Section~\ref{sec:db}). Figure~\ref{fig:architecture} shows the data flow.

Each analysis module has one non-overlapping responsibility:
\texttt{elevation\_api} (fetch/parse the DEM), \texttt{terrain\_grid} (grid and
slope), \texttt{catchment} (depression filling, flow direction, flow
accumulation, watershed delineation), \texttt{pond\_locator} (site scoring and
ranking), \texttt{geometry\_utils} (metric area/perimeter), \texttt{rainfall\_api}
(rainfall), \texttt{water\_volume} (runoff, capacity, storage curve),
\texttt{contour\_lines} (contours for display) and \texttt{visualization} (PNG
render). The route only wires them together.

\subsection{Technology Stack}
\textbf{Backend:} Python with FastAPI (async REST + auto-generated OpenAPI docs);
NumPy and SciPy for the raster/hydrology computations; Shapely and pyproj for
geometry and UTM projection; contourpy for contour extraction; httpx for async
external calls; matplotlib (lazily loaded) for server-side figure rendering.
\textbf{Front-end:} React (built with Vite) and Leaflet, with OpenStreetMap as the
base map and Esri World Imagery as a satellite toggle. \textbf{External APIs:}
OpenTopography Global DEM (SRTMGL1, 30\,m) for elevation, Open-Meteo historical
archive for rainfall, and OpenStreetMap Nominatim for place search.
\textbf{Deployment:} the compiled front-end is served as static files by the same
FastAPI process, run detached inside the provided Docker containers.

Deviations from the brief's suggested stack are deliberate. The brief suggested
per-point elevation services and a PostGIS database; we instead use
OpenTopography, which returns a whole DEM raster for the selected block in a
single request (avoiding per-coordinate rate limits that made point APIs
unusable in testing), and we use no database because the analysis is stateless and
the containers are storage-constrained (Section~\ref{sec:db}). The satellite-based
existing-pond detection (OpenCV) from the high-level design was scoped out of this
phase.

\section{Methodology}
\label{sec:methodology}
This section describes the actual algorithms and data pipeline.

\subsection{Terrain and Elevation Analysis}
For the selected bounding box the backend requests a DEM from the OpenTopography
Global DEM API (SRTMGL1, 30\,m) in ESRI ASCII-grid (\texttt{AAIGrid}) format, so
it can be parsed with NumPy and needs no native GDAL/rasterio libraries. The
raster is oriented so latitude increases with row index, no-data cells are
in-filled, and if the raster exceeds a cell cap it is stride-downsampled to stay
within memory. Local slope is computed with the Horn (1981) finite-difference
gradient, $\text{Slope}=\arctan\!\sqrt{(dz/dx)^2+(dz/dy)^2}$, with cell spacing
converted from degrees to metres. Elevation contour lines for display are
extracted from the DEM with contourpy.

\subsection{Catchment Area Delineation}
Artificial pits from the coarse DEM are first removed with the Priority-Flood
algorithm (Barnes et al., 2014), an $O(n\log n)$ depression fill. D8 flow
direction (O'Callaghan \& Mark, 1984) then routes each cell to its steepest
downhill neighbour, and flow accumulation --- the count of upstream contributing
cells --- is computed by processing the flow graph in topological order. The
catchment of a candidate site is obtained by tracing this flow network
\emph{backwards} from the site: a neighbour is added whenever its flow direction
points at the current cell, until no upstream contributors remain. The resulting
cell mask is unioned into an exact polygon (not an approximating hull, which was
found to overestimate area) and projected into the local UTM zone --- chosen
automatically from the block's location --- so area and perimeter are measured in
metres. \emph{Assumptions/limitations:} D8 assigns all flow to one neighbour, and
at 30\,m resolution small valley-scale drainage on flat terrain is only coarsely
resolved, so catchments there are conservative.

\subsection{Rainfall Data Integration}
Mean annual rainfall for the block's centre is obtained from the Open-Meteo
historical archive (daily \texttt{precipitation\_sum}), averaged over the last
several complete years to smooth wet/dry-year variation; a monthly climatology is
also returned for display. Every call has a timeout and, if the archive is
unreachable, the system falls back to a documented default annual rainfall and
marks the source accordingly, so a volume estimate is always produced.

\subsection{Pond Siting and Water Volume}
Sites are scored by combining the Topographic Wetness Index,
$\text{TWI}=\ln(a/\tan\beta)$, and the Topographic Position Index,
$\text{TPI}=z-\overline{z}_{\text{nbhd}}$, as
$\text{Score}=0.5\,\text{TWI}_n+0.5\,(-\text{TPI})_n$, then excluding cells
steeper than $15^\circ$, cells in the existing channel network (flow accumulation
above the 97th percentile plus a buffer), and candidates whose flood-fill footprint
cannot be bounded. The annual runoff a catchment delivers is estimated by the
Rational method $V_{\text{runoff}}=C\,P\,A_{\text{catchment}}$ ($C=0.3$ by
default), the basin storage capacity is measured directly from the DEM as
$\sum(w-z_i)A_{\text{cell}}$, and the collectable volume is
$\min(V_{\text{runoff}},V_{\text{capacity}})$. A stage--area--volume curve and the
depth needed to hold one year's runoff are also computed.

\section{Implementation}
\label{sec:implementation}

\subsection{Backend and API Design}
The backend exposes a small REST surface (Table~\ref{tab:api}). Requests and
responses are JSON; the schema is defined with Pydantic models and interactive
documentation is auto-generated at \texttt{/docs}. There is no authentication ---
it is an open, read-only analysis tool for the demo. Errors from third-party APIs
are handled explicitly: a malformed or out-of-range area returns \texttt{422}, an
unreachable elevation service returns \texttt{502} with a clear message, rainfall
failures fall back silently to a default, and any unexpected stage failure returns
\texttt{500} naming the stage.

\begin{table}[h]

  \begin{tabular}{p{4.0cm}p{3.5cm}}
    \toprule
    Method \& path & Purpose \\
    \midrule
    \texttt{POST /analyzeArea} & Analyse a selected map region (bbox) \\
    \texttt{POST /analyzeArea?format=image} & Same, returns a rendered PNG \\
    \texttt{POST /analyzeContour} & Analyse an uploaded contour KML/KMZ (Phase 2) \\
    \texttt{GET /health} & Service health check \\
    \texttt{GET /docs} & Auto-generated API documentation \\
    \bottomrule
  \end{tabular}

\subsection{Frontend and Visualization}
The front-end (Figure~\ref{fig:ui}) is a single-page React + Leaflet app. The user
searches a place by name (which flies the map there), frames a village-sized block,
and selects it either with a one-click ``use current view'' or by clicking two
opposite corners of a rectangle. On analysis, the map overlays the DEM contours,
the existing drainage network (blue), and for each ranked site the pond footprint
(a filled region labelled with its area), its catchment (dashed outline) and a
location marker. A side panel lists, per site, the catchment area, pond footprint,
annual runoff, basin capacity, collectable volume, required depth and a
storage-curve chart, plus a monthly rainfall chart. Results export as PNG, GeoJSON
or JSON.

\subsection{Database and Storage}
\label{sec:db}
The system uses \emph{no persistent database}. Each analysis is computed on demand
from live external data and returned directly; there is no cross-session state to
store. To avoid repeated external calls, fetched DEMs (keyed by bounding box) and
rainfall results (keyed by centroid) are held in an in-memory cache, so
re-analysing the same or an adjacent area is instant. This choice is deliberate:
the provided containers are storage- and memory-limited, a database tier would add
weight and a failure mode for no functional benefit here, and statelessness keeps
the same build trivially portable across the four systems. Exported GeoJSON/JSON
files let the user persist any result locally.

The three most significant decisions were caching, resilience and the
monolith choice. \textbf{Caching} matters because a single analysis is dominated
by the $\sim$12\,s external DEM download; caching by bounding box turns any repeat
or nearby selection into an instant response, which is what makes iterative
exploration usable. \textbf{Resilience} was forced by reality: during development
the free per-coordinate elevation service hit hard rate limits and other providers
were unreachable, so we switched to OpenTopography's single-request raster and made
every external call fail gracefully (rainfall falls back to a default, elevation
returns an actionable message). \textbf{The monolith} was chosen over the
microservice design in the original HLD specifically because the deployment targets
are 512\,MB containers --- one dependency-light process that serves both the API
and the web app is the design that actually fits the hardware.

The quantities are internally consistent: the catchment (the water source) is
always at least as large as the pond footprint (where water collects), and the
collectable volume is the smaller of what the catchment delivers and what the
basin can hold. Cross-checking against Phase 2 (which used a 1\,m contour map of
the same area) confirmed the pipeline places ponds in the same drainable zones and
away from the river.

\subsection{Performance}
A full analysis of a fresh area completes in about 12\,s, of which roughly 11.6\,s
is the external OpenTopography DEM download and $\sim$0.1--1.5\,s is the entire
CPU pipeline (flow routing, siting, catchment, geometry, volume). Cached areas
return in well under a second. Resident memory is about 160\,MB, comfortably below
the 512\,MB container limit. The backend passes 71 automated tests spanning the
parser, terrain grid, flow/catchment, pond locator, geometry, elevation parsing,
rainfall, water volume and the image-rendering path.

\section{Discussion and Limitations}
\label{sec:discussion}
The core pipeline works reliably and its behaviour is explainable end to end, and
switching to OpenTopography's single-request raster made the system dependable
where per-coordinate elevation APIs had failed. The main limitations come from
free-data resolution and scope. The 30\,m DEM under-resolves small valley-scale
drainage on flat terrain, so catchments and ponds there are modest and the D8
watershed can fragment; areas with real relief yield much larger, clearer
catchments. The rainfall archive is occasionally unreachable, in which case a
documented fallback value is used and flagged, making those volume figures
indicative rather than exact. The system also reasons purely from terrain and
rainfall: it does not know whether water already physically exists at a site, and
it does not perform the civil design of the pond. Finally, integer-metre vertical
precision in the DEM makes very gentle slopes read as near-zero. These are
properties of the input data and the chosen scope, and are stated so the
recommendations are used as a survey shortlist rather than a final design.
